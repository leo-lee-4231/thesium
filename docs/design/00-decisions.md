# 00 · 架构决策记录（ADR）

> 状态：D1–D22 已确认（2026-11-15 口径确认）。

> 关联：`01-domain-model.md`、`07-conversation-and-channels.md`

---

## 1. 背景

Thesium 的核心不是「AI 自动寻找买卖点」，而是让 AI 持续理解一个投资者的**真实持仓、投资目标与个人观点**，在市场变化或用户改口后重新审视原有判断，并给出有依据、可追溯的建议。

基线方案（交接文档）确定：单租户、BTC 现货、单个 Investment Stream、Binance 公共行情、v1 不做新闻、Thesis 分级确认、只对重要变化发通知、AGPL-3.0。**其中行情源与持仓范围已由 D18–D22 修订。**

本次新增两项产品诉求：

1. **对话窗口**：用户希望围绕某个资产，就当前价格、趋势变化和投资策略与 Agent 连续讨论。
2. **远程渠道**：Web 不一定随时可访问，希望同样的对话能力能通过 IM（微信/飞书机器人）触达。

这带来一个必须先回答的架构问题：

> 对话是「第二个产品 / 第二个 Agent」，还是「同一个 Agent Runtime 的第二种任务类型与入口」？

**结论：后者。** 否则上下文装配、工具权限、审计链路会出现两套实现，最终导致「网页里的 Agent」和「飞书里的 Agent」对同一持仓给出不一致的说法——这恰好摧毁本产品最重要的可追溯性。

## 4. 新增决策

### D9 · 对话是一等领域对象，但不是第二个 Agent

**背景**：对话看起来只是前端一个输入框，但它需要多轮上下文、工具调用、持久化和审计。如果为它单独建一套 prompt、memory 和工具，就会与定时分析分叉。

**决策**：

- 新增 `Conversation` / `ConversationMessage` 聚合，归属某个 Investment Stream。
- 对话与定时分析共用 `AgentRuntime`、`ToolRegistry`、`ContextBuilder`、LLM Provider 配置。
- 用 `AgentRun.task_type` 区分任务：
  - `MONITOR_ANALYSIS`：系统发起，输出结构化 Decision，不流式。
  - `CONVERSATION_REPLY`：用户发起，输出自然语言，可流式，可调用读取工具和提议工具。
  - `THESIS_PARSE`：把自然语言整理为结构化 Thesis 草案。
- 不为聊天单独维护模型配置、工具集或记忆库。

**理由**：

- 同一份持仓与 Thesis 必须得到同一套事实口径；双 Runtime 迟早漂移。
- 工具权限只需定义一次（见 `03-agent-runtime.md` 的权限矩阵）。
- 每次对话回复都能落到 `agent_runs`，与 Decision 共享同一条审计链。

**后果**：

- Runtime 的抽象必须同时容纳「结构化输出」和「多轮流式输出」，不能写成只服务定时任务的脚本。
- Prompt 分层中「Task Prompt」成为真正的变量，ContextBuilder 需要支持按任务裁剪上下文。

**否决的备选**：独立聊天机器人（例如直接接一个通用 Agent 框架）。上下文、工具、审计三处重复，且难以保证「聊天里说的」和「监控里判的」一致。

---

### D10 · Headless 核心 + 薄表面

**背景**：Web、飞书、微信、未来的 MCP/CLI 都想要同一能力。若每个入口各写一套业务逻辑，产品会迅速碎片化。

**决策**：

- 业务规则只存在于 Application Service 与 Agent Runtime。
- Web 前端、IM 渠道网关、未来的 MCP Server 都是**客户端/适配器**，不做领域判断。
- 渠道网关与 API 共享同一应用服务包：同进程直接调用；拆进程时走内部 API，不复制逻辑。
- 前端不直接拼 Prompt、不直接读数据库。

**理由**：

- 入口数量会增加，但核心只有一份；新增渠道是适配器工作量，不是产品分叉。
- 单测可以围绕应用服务做，不依赖 HTTP 或 IM SDK。

**后果**：

- API 契约与 Application Service 契约需要显式定义（`05-api.md`）。
- 「Web 是主界面」的假设被取消：飞书里也能完成核心操作，Web 更像账本与审计视图。

---

### D11 · 渠道适配器抽象；飞书先行；个人微信不做

**背景**：用户提出微信/飞书机器人。两者在官方支持度、接入成本、封号风险上完全不同。

**决策**：

- 定义统一 `ChannelAdapter`（入站解析、出站发送、确认卡片/文本）与 `InboundMessage` / `OutboundMessage`。
- v1 首个真实渠道：**飞书自建应用**，使用 WebSocket 长连接接收事件，无需公网回调地址。
- 企业微信、微信公众号/微信客服作为后续适配器，接口预留，不在首版实现。
- **个人微信不做**：没有官方 Bot API，现有桥接方案违反平台条款、随时可能封号，且消息可靠性无法承诺。

**理由**：

- 飞书官方支持机器人、长连接、手机推送和交互卡片，适合自托管在家用网络后面。
- 个人微信的「方便」建立在账号风险上；对一个能读取真实持仓的 Agent，这不是可接受的依赖。

**后果**：

- 飞书之外的用户暂时只能使用 Web；若用户主要生活在微信，需要重新评估企业微信/公众号路线（见开放问题 Q2）。
- 渠道能力有明确的能力矩阵，不假装所有渠道都支持卡片、主动推送或群聊。

---

### D12 · 渠道身份 = 配对码 + 白名单 + 可撤销绑定

**背景**：v1 单租户、无登录。IM 机器人如果对任何人开放，等于把「你的持仓 + 你的观点 + 可触发的分析」暴露给外部；如果直接信任消息里的 `user_id`，则等于没有身份。

**决策**：

- Web 设置页生成一次性配对码（8 位，10 分钟 TTL，数据库只存 hash）。
- 用户在 IM 中向机器人发送 `/bind <code>`；网关校验后把 `(channel, external_user_id)` 绑定到本地用户。
- 未绑定发送者一律拒绝，并提示去 Web 配对；绑定可在 Web 立即撤销。
- **v1.0/v1.1 渠道只读**，没有确认类写操作，因此不引入渠道确认令牌。
- 未来若开放渠道写操作，再使用绑定到 Proposal + 用户 + TTL 的一次性令牌，单次使用；不复用聊天里的「好的」。
- 入站校验平台签名/长连接身份；限制单用户速率与消息长度。

**理由**：

- 绑定即凭证。机器人能看到组合，必须按高敏资产对待。
- 单租户没有登录态，白名单是最小可用的访问控制。
- 只读渠道把「远程误操作」风险降到零，也让 v1.1 的确认复杂度显著下降。

**后果**：

- 用户换手机/换飞书账号需要重新配对；这是有意的摩擦。
- 渠道消息在平台侧可见，需在文档中明确「数据会经过 IM 平台」，不宣称端到端私密。

### D13 · 对话记忆不越界

**背景**：对话会自然产生大量「我觉得短期要跌」这类半结构化判断。如果把这些原文无差别注入定时分析，等于让 Agent 悄悄把聊天内容当成用户正式观点，违反「AI 推断不得记为用户观点」。

**决策**：

- 对话消息全量持久化，按 conversation 保留。
- 超出上下文窗口后使用**滚动摘要**，摘要仅服务该对话，不跨 conversation 复用。
- 定时分析**不读取原始聊天记录**；只读取已生效的 Thesis 版本、持仓快照、历史 Decision 和显式保存的 Observation。
- 聊天中出现的观点变化不会被自动记录；用户需到 Thesis 编辑器显式修改并确认，才成为新的 Thesis 版本。
- 聊天回复可以引用「你当前 Thesis 说……」，但不能声称「你刚才在聊天里说过……」被写入了正式观点。

**理由**：

- 守住「真实持仓 / 用户观点 / AI 推断」三分。
- 对话保持低摩擦，正式观点保持高门槛；AI 草案只能通过编辑器确认进入版本。

**后果**：

- 用户若想「把刚才聊的结论记下来」，需要多一步确认；这是产品有意设计的收据。
- 对话摘要需要版本化（`summary_through_seq`），避免摘要漂移无法解释。

---

### D14 · 正式变更只由用户显式提交或确认

**背景**：用户可能说「帮我记一下，我刚在 92,000 卖了 0.2 BTC」或「我改成短期看空到 65,000」。但本次口径确认：**v1.0 的对话是只读的**。对话可以讨论、可以给操作框架，但不能创建 Proposal、不能改任何正式事实。

**决策**：

- 对话工具集只包含读取类 + 纯计算类（如 `simulate_position_change`），没有 `propose_*`，没有 `save_*`。
- Thesis 的正式变更只能通过 Web 的 Thesis 编辑器：用户手动编辑，或在编辑器里显式点击「AI 润色」改善表达、「AI 帮我整理」触发 `THESIS_PARSE` 生成结构化草案；用户编辑并确认后才写入新版本。
- 持仓变更只能通过「记录成交 / 修正持仓」表单，由用户提交。
- `Proposal` 表保留给未来的渠道写操作；**v1.0 不产生 Proposal**，AI 结构化草案经编辑器确认后直接形成 Thesis 版本。
- 所有正式变更留 audit log；AI 生成的部分标注 `source=AGENT` 与 `source_agent_run_id`。

**理由**：

- 只读对话把「模型误解用户意图 → 悄悄改观点」的风险降到零。
- 用户仍然可以在对话里得到操作策略和心理支持，只是「记录」这一步必须由清醒的用户自己完成。
- 减少 v1.0 的确认 UI 与并发校验复杂度。

**后果**：

- 用户说「帮我改成看空」时，Agent 只能解释并给出修改建议，不能代劳；需要引导到编辑器。
- 未来若开放渠道写操作，再引入一次性确认令牌与 Proposal 流程。

### D15 · 对话的语气：操作框架与心理支持，而不是预测与催促

**背景**：用户明确希望对话能提供「合适的操作策略或心理按摩信息」。行情剧烈波动时，投资者最需要的往往不是更多预测，而是把事实、情绪和纪律分开。

**决策**：

- 允许给出**情景化操作框架**（if-then），但必须绑定用户自己的 Thesis、风险预算和失效条件；不给确定性的点位预测。
- 允许**情绪支持**：承认波动带来的压力、帮助区分「价格事实」与「情绪叙事」、提醒仓位与风险预算、建议暂停而不是立刻操作。
- 不做的：承诺收益、制造 FOMO、羞辱用户、催促交易、编造新闻、提供医疗/心理治疗建议。
- 对话回复要求区分：事实 / 用户观点 / AI 推断 / 建议。
- 若用户表达严重情绪困扰，先共情并建议联系可信任的人或专业帮助；不继续给交易建议。

**理由**：

- 「心理按摩」如果变成讨好或保证，会加剧过度交易；它应该服务于纪律，而不是替代纪律。
- 这与产品定位一致：AI 帮你看清，不替你下手。

**后果**：

- System Prompt 与评估集需要包含语气与边界用例。
- 对话质量不能只看「答得对不对」，还要看「有没有怂恿不该做的操作」。

### D16 · Thesis 编辑是独立窗口；AI 润色不改事实，用户最终确认

**背景**：修改 Thesis 时，用户常需要 AI 帮助润色表达。这不同于对话，也不等于让 AI 重写观点。

**决策**：

- Web 提供**独立的 Thesis 编辑页**（不是聊天面板）：左侧原文/编辑区，右侧 AI 润色建议，下方结构化字段与 diff。
- 新增 `THESIS_POLISH` 任务：只改善表达、结构、清晰度；不新增/删除数字、目标价、方向、周期、约束或事实；不把观点改写成投资建议。
- 双文本保存：
  - `original_text`：用户在本版本起草时的原始输入，永不覆盖；
  - `final_text`：用户最终确认的正文（可采用润色，也可手动编辑；为空时回退 `original_text`）；
  - Agent 上下文使用 `final_text or original_text`；
  - `polish_agent_run_id` 记录润色 Run，`source_agent_run_id` 记录结构化 Run。
- 润色结果**不自动保存**：用户必须点击「采用润色」或手动编辑，再提交；提交后仍按 MATERIAL/MINOR 走确认。
- 对话窗口仍只读：不能触发润色、不能保存。
- 润色输出必须带 `change_notes` 与 `warnings`；UI 展示 diff，用户可逐段接受/拒绝。

**理由**：

- 满足「AI 帮忙润色」的真实需求，同时不把「表达改善」混成「观点变更」。
- 原文与确认正文分离，既保留用户原话，又允许更清晰的正式版本。
- 与 D14 一致：AI 不直接写正式事实，最终确认权在用户。

**后果**：

- 数据模型多两列（`final_text`、`polish_agent_run_id`）；Agent 读取逻辑需回退。
- Prompt 与评估集需覆盖「润色不改变事实」。
- UI 多一个编辑页面，但不增加对话写权限。

### D17 · 数据库保持 PostgreSQL；SQLite 评估后不采用

**背景**：单人自托管 / NAS 场景下，考虑用 SQLite 降低部署重量。

**评估**：

- SQLite 对 v1 负载足够：单用户、每小时分析、持仓/消息写入量很小，WAL 可以撑住。
- 但 SQLite 没有原生精确十进制，金额必须改成整数最小单位；没有 `FOR UPDATE SKIP LOCKED`；`JSONB` / `NUMERIC` / 时区 / UUID 有方言差异；Alembic 需要 batch 模式；维护双后端测试成本高。

**决策**：

- v1 保持 PostgreSQL 16。
- 用「小配置」降低重量：`shared_buffers=64MB`、`max_connections=20`、只绑定 `127.0.0.1:5432`；`make backup` 提供 `pg_dump`。
- 不维护双数据库后端；SQLite 只作为未来极简部署的备选，不在 v1 实现。

**理由**：

- 金额精度与审计一致性优先；这是产品的地基。
- NAS 上多一个 Postgres 容器的成本可接受，真正省下的是「改 schema + 双方言测试」的时间。
- 避免为了轻量而引入整数最小单位、队列改写等更大的复杂度。

**后果**：

- 部署需要备份/恢复脚本；已提供 `make backup`。
- 未来若确实需要单文件部署，再评估 SQLite 与迁移路径。

### D18 · 首个行情 Provider 改为 OKX 公共 API

**背景**：交接文档 D2 选的是 Binance，但用户日常使用 OKX，且 Binance 公共 API 在部分网络不可达。这不是技术必需，而是使用习惯与可达性问题。

**决策**：

- 首个实现 `OKXProvider`，只使用公共行情接口，不需要 API Key。
- 首批 Instrument：`BTC-USDT`（SPOT）、`BTC-USDT-SWAP`（SWAP）；ETH 后续同构加入。
- `Instrument` 继续用 `provider + symbol + market_type` 唯一；Binance 仅保留适配器接口，不在 v1 实现。
- OKX 日线边界可能与 UTC 不同；内部统一存 UTC，必要时由 1H/4H 聚合出 UTC 日线，避免边界歧义。

**理由**：

- 用户实际使用 OKX，数据源与交易习惯一致。
- 公共接口免 Key、支持现货与永续、字段足够中长线分析。
- 保留 Provider 接口，不把领域模型绑死在 OKX。

**后果**：

- P1 需要验证 OKX 的限频、字段、时间戳与 K 线边界。
- Provider 契约测试覆盖 SPOT 与 SWAP；Binance 留待后续。

### D19 · 合约只做“观察数据”，不混入盈亏

**背景**：用户关心中长线的杠杆与情绪背景，但不需要超短线的盘口/逐笔精度。

**决策**：

- 从 OKX 读取 SWAP 的 mark price、funding rate、open interest，可选 basis。
- 这些数据作为 Agent 上下文中的“杠杆/情绪背景”，**不参与**现货或合约持仓的 PnL 计算。
- UI 明确标注“观察数据”，与“持仓数据”分开。

**理由**：

- 观察数据能提升中长线判断质量，但不应与账本混在一起。
- 避免把 funding/OI 误当成持仓成本或盈亏。

**后果**：

- `market_snapshots` 增加衍生品观察字段；与 `derivative_positions` 的计算分离。

### D20 · 用户界面用 Investment Product，内部保留 Stream

**背景**：用户认为 “Investment Stream” 不贴合，界面上应该看到关注资产（BTC、ETH、某只美股），一张卡点进去查看、问答、配置。

**决策**：

- 用户界面统一使用 **Investment Product / 投资产品**；卡片按“一个资产一张”展示。
- 内部聚合保留 `InvestmentStream`：它承载该资产的 Thesis、持仓、分析历史；未来同一资产的多套策略（长期/波段）作为产品内的 Stream Tab。
- v1 产品与 Stream 1:1；API 路径暂时保留 `/streams`，不为了文案改表名。
- 界面文案不出现 “Stream” 这个词。

**理由**：

- 用户语言更自然；领域模型不必为 UI 文案返工。
- 同一资产多策略是真实需求，Stream 仍有存在价值。

**后果**：

- 文档与代码中需要维护“Product（UI）/ Stream（domain）”的映射。
- 未来若确实要重命名表，再做一次性迁移。

### D21 · 支持 USDT 本位永续持仓；清算价由用户输入

**背景**：用户希望合约持仓也能记录和计算，但不需要平台去猜交易所的保证金档位。

**决策**：

- v1 只支持 **USDT 本位永续、单向持仓**（long/short 二选一）；币本位、交割、期权、双向持仓不做。
- 用户录入：方向、数量（以 BTC 等基础资产计）、开仓均价、杠杆、保证金、**清算价**；可选手续费。
- 本地计算：notional、未实现盈亏、ROE、保证金占用、距清算价百分比、风险预算占用。
- **不估算清算价**：清算价以用户从交易软件看到的值为准；没有填就显示“未提供”，不猜。
- 资金费率作为可选流水事件记录，不自动计算。
- 新增 `derivative_positions` / `derivative_position_events` / `derivative_position_snapshots`，不与现货 `positions` 混表。

**理由**：

- 用户输入 + mark price 足以得到可信的 PnL 与风险距离。
- 交易所清算价依赖风险档位/保证金模式/费用，平台自行估算反而会制造“假精确”。
- 单向持仓先覆盖主流用法，避免双向/对冲模式的复杂语义。

**后果**：

- P2 增加合约持仓与风险计算；P4/P5 的上下文和工具需要覆盖两类持仓。
- 数量单位需要明确（基础资产数量 vs 张数）；v1 用基础资产数量，UI 可显示 OKX 张数换算提示。

### D22 · Decision 增加合约建议，但必须与持仓方向一致

**背景**：有了合约持仓后，单一 `BUY/SELL` 语义不够：加现货、开多、平多、开空是不同动作。

**决策**：

- 保留整体 `decision`（BUY/SELL/HOLD/REDUCE/WAIT/REVIEW）作为摘要。
- 增加可选 `derivative_recommendation`：

```json
{
  "action": "REDUCE_LONG",
  "size_change_pct": "25",
  "rationale": "……",
  "invalidation_conditions": []
}
```

- 动作枚举：`OPEN_LONG` / `INCREASE_LONG` / `REDUCE_LONG` / `CLOSE_LONG` / `OPEN_SHORT` / `INCREASE_SHORT` / `REDUCE_SHORT` / `CLOSE_SHORT` / `ADJUST_MARGIN` / `HOLD` / `NONE`。
- 校验：单向持仓；`OPEN_*` 只在无持仓时；`INCREASE/REDUCE/CLOSE` 必须匹配当前方向；`CLOSE_*` 必须有持仓；禁止同一轮同时开多与开空。
- 有合约持仓时，`derivative_recommendation` 必填（可以是 `HOLD`）；无持仓时可为 `NONE`。
- 非 `HOLD/NONE` 的合约建议默认 HIGH，进入通知策略。

**理由**：

- 避免“BUY 到底是买现货还是开多”的歧义。
- 让审计能回答“当时对哪个方向、哪个动作给了建议”。

**后果**：

- Decision Schema、Validator、通知策略、对话上下文都要扩展。
- 图标/文案需要把“现货建议”和“合约建议”分开显示。

## 7. 一句话结论

**不要让对话变成另一个 Agent。** 让它成为同一 Runtime 的另一种任务、同一份上下文的另一种问法、同一条审计链的另一个入口；而正式事实只能由用户在编辑器/表单里显式提交或确认——v1.0 连 Proposal 都不由对话创建。
